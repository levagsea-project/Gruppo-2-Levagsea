# Design decisions



Commit log of taken decisions. Status: **applied** (in `data/` and `docs/rules/`), **rejected** (kept so the choice is never re-suggested).

**ID format:** `YYYY-MM-DD-short-slug` (date of the decision, lowercase slug, unique). No sequential numbers, so two branches never collide. Reference a decision by its full ID. Old `D-nn` IDs were converted on 2026-11-07.



| ID | Decision | Status |
|---|---|---|
| `2026-11-01-camaleonte-suit` | **Camaleonte does not count as another suit for synergies** (already in vocab `E55`); only for Colore and Quattro dello stesso seme. Text mirrored in `keyword.json`. | applied |
| `2026-11-01-suit-themes` | **Suit themes**: Vincolo adjacency, Frattura breakthrough, Spira adaptation + growth, Vestigio persistence. `evolution` is a mechanism, not a theme; Spira's pull on Evolutions is `evolution_slot_fill_pct`. | applied |
| `2026-11-01-ability-caps-by-class` | **Ability caps by class**: `capped` = 1 rank (max 4 per deck), `limited` = 2-3 ranks, `open` = any rank. Busted abilities are capped; capped abilities may share a rank, so the 4-card cap is combined. Rank does not decide the ability: an Ace may carry any open ability. | applied |
| `2026-11-01-evolution-inherits-ranks` | **An Evolution that grants a capped/limited keyword inherits its ranks.** Closed a leak (Mimetico on rank 3 granted Camaleonte, rank 2). | applied |
| `2026-11-01-engine-deployment` | **Engine deployment**: standalone Java 25 + Spring Boot 4.1.x, packaged as a Docker container and served on a configured HTTP port as a separate microservice. | applied |
| `2026-11-01-validate-py-reference` | **`data/validate.py` is the reference validator** (ten checks from `data/AGENTS.md` §7, cap model, `ranks.json`, fit targets). | applied |
| `2026-11-04-database-postgresql` | **Database engine**: changed the backend's relational database from MySQL 8.4.x to PostgreSQL 16 (JDBC connection, Hibernate default dialect). | applied |
| `2026-11-05-repricing-stat-scale` | **Repricing against a working stat scale** (ATK about 4000, DEF 1.5-2.5 x ATK, life 12000, about 9 turns). Scudo x 15 -> 25 with cost 3 (per-x 0.12), Sostegno cost 5 -> 9, Insaziabile 10% -> 15% per stack with cost 4, Muro bonus 10% -> 30%, Custode cost 10 -> 15. Rigenerante unchanged (already fair at this scale). Numbers come from a simplified simulation, not from real cards. | applied |
| `2026-11-05-deck-cap-swingy-abilities` | **Combined deck cap on swingy abilities (max 4 cards per deck).** Rejected: abilities are limited by which ranks may carry them, never by a deck-level count. Rank access also makes high-Tier cards wanted without making them stronger, and keeps low-Tier decks competitive. | rejected |
| `2026-11-05-frattura-rework` | **Frattura reworked**: tier 3 +[1200] ATK (was 300, rescaled by `2026-11-05-ruleset-clarifications-rescale`); tier 4 keeps spill x[1.2] and also treats the target's DEF as [80]% for spill; tier 5 adds spill x[1.2] to its 50% DEF rule so it is a strict upgrade over tier 4. Ruleset 7.10.6 updated to match. | applied |
| `2026-11-05-rank-concentration-unlimited` | **Rank concentration is not limited.** Decks built on few ranks hit pairs and better much more often and win clearly more; this is accepted by design. | applied |
| `2026-11-05-ruleset-clarifications-rescale` | **Ruleset clarifications and placeholder rescale.** Spira 3 counts only your own Evolutions (new `scale_by` value `own_evolutions_triggered`); spill has a minimum of 0; the turn-50 tie-break uses the poker hand of the last Evaluation; Vestigio 3 bonus goes to the replacement of any suit. Flat synergy placeholders doubled for the working stat scale (ATK about 4000): Vincolo [600]/[400]/[1000], Frattura 3 [1200], Spira 3 [200] per Evolution, Vestigio 3 [1000] and 4 [1400]; Scudo flat range [400, 1600]. One-suit decks gain about +2 to +2.5 points each in simulation. Spells and equipment stay in the ruleset for later. | applied |
| `2026-11-06-flyway-migrations` | **Database schema is managed by Flyway migrations** (`backend/src/main/resources/db/migration`, one file per domain, never edited after merge). Hibernate only validates (`ddl-auto: validate`). Needed because the schema relies on triggers, partial/composite keys and CHECKs that Hibernate cannot generate. | applied |
| `2026-11-06-pools-per-faction` | **Pools are per faction; card identity is separate from versioned content.** `pool_snapshots` has one faction each; `cards` is the stable identity (code, faction, kind, suit, rank); `card_definitions` holds stats and abilities per snapshot. Owned card instances point to `cards`, so a rebalance never migrates collections. A match records two pool snapshots (one per player). | applied |
| `2026-11-06-decks-reuse-cards` | **Decks reuse cards.** A deck is only a saved selection: the same card instance may be in several decks. Deck structural rules are DB constraints (`deck_slot` unique per deck: one creature per suit and rank, one copy of each spell/equipment; owner, faction and snapshot consistency via composite FKs). The 32-card total and per-faction limits stay in the backend. | applied |
| `2026-11-06-spells-equipment-effect` | **Spells and equipment are cards of their own kind** (`kind` SPELL/EQUIPMENT, no suit/rank/stats). Their effect is written in `abilities`, like every card (`2026-11-07-cards-share-abilities`); the separate `effect` column no longer exists. Abilities are opaque JSON for the backend; the engine owns their meaning. | applied |
| `2026-11-06-append-only-triggers` | **Append-only tables are enforced by triggers**: ledger, pool snapshots, cards, card definitions, ownership history, matches. A snapshot is sealed when its creating transaction ends (definitions cannot be added later). Card instances can never be deleted and only `owner_id`/`acquired_at` may change. | applied |
| `2026-11-06-admins-do-not-play` | **Admins manage the game but do not play it.** `ADMIN` accounts never hold credits (DB CHECK `users_admin_has_no_credits`) and, enforced by the security layer, cannot use game endpoints (packs, decks, trades, challenges). Admin grants record the admin's user id in `card_instances.origin_ref` / `credit_transactions.reference_id`. An admin who wants to play uses a separate `PLAYER` account. | applied |
| `2026-11-06-match-start-methods` | **Two ways to start a match: player challenge and automatic matchmaking.** A challenge goes to a chosen player who accepts (choosing decks) or declines; it expires (`challenges.expires_at`, status `EXPIRED`). Matchmaking picks an opponent and plays immediately, even if they are offline. `match_series.kind` is `CHALLENGE` or `MATCHMAKING`; `challenge_id` is set only for challenges. Player A is always who started the series (see `2026-11-06-series-and-games`). | applied |
| `2026-11-06-series-and-games` | **A series is what gets started; it holds one or more games.** `match_series` (kind, format `SINGLE` or `FACTION_SWAP`, players, status, outcome) owns the games in `matches` (`series_id`, `game_number`). In `FACTION_SWAP`, player A plays one faction against the opposite faction of player B, factions swap for game 2, and each further game swaps again. Seats never change (A is always the initiator); the faction a player used is the faction of that game's pool snapshot. Challenges lock one deck per side and faction (`challenge_decks`). The schema records each game and does not encode how many games are needed or which factions game 3 uses (open, `2026-11-06-faction-swap-open-rules`). **Start method and format are independent**: challenge and matchmaking both work with `SINGLE` and `FACTION_SWAP`. Triggers enforce that a `SINGLE` series has only game 1 and a `SINGLE` challenge locks one deck per side. | applied |
| `2026-11-06-offline-defense-decks` | **Offline defence uses a defense deck per faction, and the opposite faction is selected.** `decks.is_defense` marks it, at most one per owner and faction (up to two per player). In matchmaking the defender's deck is the one of the **opposite faction** to the attacker's deck in each game, stored in the match like any other snapshot. Over a `FACTION_SWAP` series both defense decks are used. | applied |
| `2026-11-06-starter-decks` | **Every player starts with 2 pre-made decks** (one per faction) built from `STARTER` card instances, and must always keep at least one legal deck per faction (backend rule). Open: what happens when a ruleset or pool change makes a player's last legal deck illegal (see `2026-11-06-ruleset-change-illegal-deck`). | applied |
| `2026-11-06-match-notifications` | **Match notification flag for both players.** `match_notifications` has one row per player of every match; unread = `seen_at IS NULL`. A player who gets the result at once (e.g. the attacker, in the response) has the row created already read; anyone else (offline defender, challenger whose challenge was accepted later) gets it unread and receives it at next login. A trigger only allows the two players of the match. `matches` stays immutable. Ratings are not stored yet; they can be added later with a new migration and rebuilt from the stored matches. | applied |
| `2026-11-07-multiple-keywords-per-card` | **A card may carry several keywords, still only one evolution.** `balance.globals.card_ability_slots.keyword` goes from 1 to 3 (placeholder); `evolution` stays 1. `keywords` on a card is a list of distinct ids resolved in list order. No code enforced the old limit (backend stores abilities as opaque JSON; the engine has no card model yet). Open: `pool_generation.keyword_slot_fill_pct_by_tier` is per card, not per slot, so extra slots need their own fill rule. | applied |
| `2026-11-07-hand-multipliers-in-balance` | **Poker hand spill multipliers live in `balance.json` → `hand_multipliers_permille`**, keyed by `HandType` name (12 hands from ruleset 7.8, plus `NONE` = 0 for a board with no creatures), in per mille. The engine reads them through `Ruleset.handMultiplierPermille`; no number is hard-coded in code. Values are the ruleset placeholders. | applied |
| `2026-11-07-missing-kicker-is-zero` | **A missing kicker counts as 0 when comparing hands.** When two hands of the same type have tie-break lists of different length (fewer creatures on one board), each missing value is 0, so a kicker of 5 beats an empty card. Hand ranks are compared first, so an empty card never outweighs a higher rank. Applies at the turn-50 tie-break (ruleset 11.4). Ruleset 7.5 does not state it yet. | applied |
| `2026-11-07-cards-share-abilities` | **Creatures, spells and equipment write their abilities the same way.** Every card has an ordered `abilities` list. An ability is either a reference to a keyword or evolution by id with the card's own params (`{"id": "K_SCUDO", "params": {"x": 15}}`) or a whole effect written as expansions. Any card may have either. The vocabulary, loader, binder and validator are shared; spells and equipment differ only in when they fire (on draw, class I) and in which targets apply (none that need a trigger's context). | applied |
| `2026-11-07-four-of-a-suit-kicker` | **A Four of a suit is also compared by its fifth creature (kicker), which does not attack.** Ruleset 7.5 now says so; a missing kicker counts as 0 (`2026-11-07-missing-kicker-is-zero`). Tests: `HandEvaluatorTest`, `HandCompareTest`. | applied |
| `2026-11-07-no-target-no-attack` | **An attacker with no target does not attack.** If no enemy lane holds a creature that can be targeted, the attacker has no target and does nothing, like an attacker whose target is destroyed (9.3). Nothing hits the player. Ruleset 8.1 updated. In the engine such an attack belongs to Cycle 2 and is skipped there. | applied |
| `2026-11-07-destroyed-creatures-flagged` | **A destroyed creature is flagged, stays in its lane until Refill, and cannot be targeted unless an effect says so.** It is removed in Refill (10.2). Ruleset 3.2.6 updated. Targeting ignores flagged creatures by default. | applied |
| `2026-11-07-cycle-2-order` | **Cycle 2 attacks run one at a time, ordered by the attacker's lane number, both players interleaved.** Each attack applies at once, so later attacks see the DEF left by earlier ones. A tie on the same lane number (possible only with effects) uses the resolution order below. If the target is destroyed, or the attacker was destroyed before being called, it does not attack. Cycle 2 spill is always normal. Cycle 1 stays simultaneous: a creature destroyed in it still deals its damage. Ruleset 9.2 and 9.3 updated. | applied |
| `2026-11-07-resolution-order-faction-then-side` | **Order between players: Potenze Artificiali, then Resistenza Umana, and with the same faction player A (who started the match) first.** Applies to the stack (4.3), Refill draws (10.3) and Cycle 2 ties (9.3). Strict player order was considered and rejected: the faction order is in the ruleset and does not give the challenger an advantage in every game. | applied |
| `2026-11-07-refill-spells-equipment-immediate` | **A spell or equipment drawn in Refill is triggered at once and the player draws another card** (10.5, 10.6, confirmed). An equipment applies to the next creature drawn in the phase, and is lost if the deck runs out (10.8). The engine calls a hook that does nothing until card data exists; the tests for it are a `TODO(spells-equipment)`. | applied |
| `2026-11-07-deck-top-is-index-0` | **The top of a deck is index 0 of its list.** Setup shuffles with Fisher-Yates and draws from index 0. Fixed once because it changes every draw and every golden file. Engine convention, no ruleset change. | applied |
| `2026-11-08-atk-clamped-at-zero` | **Effective ATK never goes below 0.** A debuff that would take ATK below 0 leaves a creature that hits for 0: it deals no damage, causes no spill (`max(0, ATK - DEF)`) and never heals the target. Chosen for design clarity and to keep debuff stacking safe. Ruleset 9.1 updated. Engine: `Damage.effectiveAtk`. | applied |
| `2026-11-08-db-uses-engine-names` | **The database stores the engine's own names for suit and rank.** `cards.suit` is the `Suit` constant name (`VINCOLO`, `FRATTURA`, `SPIRA`, `VESTIGIO`), `cards.rank` is a smallint 1..13 (Ace = 1, Jack = 11, Queen = 12, King = 13). Faction and subfaction keep their data-file names (`Resistenza Umana`, `Adattati`), which `Faction.dataName()` and `Subfaction.dataName()` return, so no mapper is needed. `card_definitions.abilities` is a JSON array, never null, for every kind. | applied |
| `2026-11-11-error-codes-not-text` | **The API returns error codes, not translated text.** Codes (`ErrorCodes`) are keys of `data/labels/<locale>.json`; the frontend picks the language. Validation errors become `fieldErrors: {field: {code, params}}` (before: `{field: text}`), a breaking change of the 400 body that the Web team must be told about. Labels cover errors and base game vocabulary (factions, suits, phases, hand types); keywords and other effect text are left out until the MVP card set is decided. English game terms are provisional; faction, subfaction and suit names stay Italian. | applied |
| `2026-11-08-equipment-discard-after-use` | **An equipment goes to the discard pile after it is applied (or lost), not when drawn** (ruleset 10.7). A spell is discarded right after its effect. The `onEquipment` hook therefore runs while the equipment is not yet in the discard pile. Tests: `RefillTest`. | applied |
| `2026-11-14-mvp-ability-set` | **Only the abilities the engine resolves are live; the rest is parked.** Live keywords: Scudo (C, damage taken), Perforante (C, ignores reductions, tests modifier order against Scudo), Insaziabile (T, ATK per kill with `max_stacks`) and Traboccante (R, spill multiplier): one per resolution class, each changing damage at a different point. No Evolutions. The 12 suit synergies stay live (ruleset 7.10). Every other keyword and Evolution, and every vocab entry, class rule and combination rule the live data does not reach, moved to `data/parked/` with its balance entry, role affinity and open decisions. Numbers unchanged. IDs keep their values and stay reserved (renumbering would break every parked reference); the next free ID counts parked ones. `data/parked/` is excluded from the engine jar. | applied |
| `2026-11-14-spill-after-mitigation` | **Spill uses the damage actually dealt, not the effective ATK.** Spill = floor(max(0, damage dealt - target DEF before the blow) x multiplier / 1000), where damage dealt is the effective ATK after the target's damage reductions (Scudo, `E28`). So Scudo lowers spill too. Changes the wording of ruleset 9.6 (see `2026-11-14-ruleset-wording-spill-stack` in KNOWN-ISSUES). | applied |
| `2026-11-14-stack-resolves-when-quiet` | **The stack resolves once nothing more is being added to it, as in Magic.** It starts after each batch of simultaneous events: after all Cycle 1 blows, after each Cycle 2 attack, after each card drawn in Refill (10.5) or placed at setup. Effects triggered together are pushed in lane order, Potenze Artificiali first (ruleset 4.3). An effect triggered while another resolves goes on top and resolves next. The game moves on only when the stack is empty. There is no priority and no response (players decide nothing). An effect whose target is destroyed when it resolves does nothing and is logged as fizzled ("le creature distrutte non sono influenzate"). Safety net: more than 1000 resolutions in one stack stop the simulation with an engine error. | applied |
| `2026-11-14-traboccante-multiplies` | **Traboccante multiplies the hand multiplier, it does not set it.** As `E21` says: the multiplier used for that attack's spill is floor(hand multiplier x factor / 1000), e.g. Pair 1100 x 1200 = 1320. The keyword description said "è ×1.2"; corrected as an erratum. | applied |
| `2026-11-14-traboccante-stacks-with-frattura` | **Traboccante stacks with Frattura 4 and 5.** Every `E21` on an attack multiplies in order (hand multiplier x 1200 x 1200 = x1.44), the normal multiplicative step of Regola d'Oro 2. Replaces the `max_with` rule with Frattura 4, which made Traboccante do nothing on Frattura attackers with Frattura 4 active, where its `breakthrough` theme draws it most often (while still paying its stat cost and the theme tax), and which did not cover Frattura 5 (same x1.2, replaces Frattura 4), so the keyword was weaker with 4 Frattura than with 5. Numbers unchanged; if simulation shows too much spill, lower Traboccante's factor (open decision in `balance.json`). | applied |
| `2026-11-14-match-log-schema` | **The Software team owns the MatchLog and match input schemas; the Web team follows them.** JSON Schema (draft 2020-12) in `game-engine/src/main/resources/schemas/` (`match-input.schema.json`, `match-log.schema.json`, plus `match-log.example.json`), bundled in the jar so the engine-service can publish them. Keys are snake_case like `data/`. Numbers are integers only. Canonical form: UTF-8, LF, 2-space indent, keys in schema order, trailing newline. `result_hash` is the SHA-256 (lowercase hex) of the canonical bytes of the log without the `result_hash` key, which is then added as the last key. `ruleset_hash` is the SHA-256 of the canonical serialization of the live rule pack (`vocab`, `keyword`, `evolutions`, `synergies`, `balance`, `invalid-combinations`, in that order, as a JSON object keyed by file name). The input carries full card definitions (the backend's deck snapshots stay opaque to it). Faction, subfaction, suit and hand type are language-neutral codes, the engine's constant names (`RESISTENZA_UMANA`, `ADATTATI`, `VINCOLO`, `HIGH_CARD`); the frontend shows the label `game.<group>.<code in lower case>` from `data/labels/<locale>.json`. Same rule as the pack and collection endpoints (`2026-11-12-faction-ids-neutral`, branch 20). Rank stays the number 1..13 (`2026-11-08-db-uses-engine-names`). | applied |
| `2026-11-14-hand-type-label-keys` | **Hand-type labels are keyed by the engine code.** `game.hand_type.<HandType in lower case>` (`game.hand_type.high_card`, was `game.hand_type.carta_alta`), so every label key is `game.<group>.<code in lower case>`, the code the API and the MatchLog send. Added `game.hand_type.none` (board with no creatures). Texts unchanged. `data/validate.py` takes the codes from `balance.json` -> `hand_multipliers_permille`. No code read the old keys. | applied |
| `2026-11-14-schema-validator-test-only` | **The MatchLog schema is checked in the engine tests with a JSON Schema validator** (`com.networknt:json-schema-validator`, test scope, exact version). It never reaches the engine jar or the Docker image; the enforcer rule still bans Spring. Golden files prove the exact numbers and repeatability. | applied |
